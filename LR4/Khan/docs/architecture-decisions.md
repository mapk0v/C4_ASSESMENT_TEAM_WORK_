# Архитектурные решения и ограничения ЛР4

## 1. Что подтверждено ранее

- Сервис `analytics_service` работает внутри ИС и вызывается Backend (`api_gateway`) по gRPC/HTTP2.
- Внутренние компоненты Analytics: `grpc_handler`, `analytics_coordinator`, `rating_calc`, `risk_detector`, `report_builder`, `analytics_repo`.
- Источники данных — таблицы PostgreSQL, доступ через `analytics_repo`.
- Analytics может направлять в Notifications событие о выявлении группы риска, но сам калькулятор `rating_calc` **не** отправляет уведомления.
- Вуз использует оценки **0–54 за каждую дисциплину и модуль**: 0–24 «не сдал», 25–34 «удовлетворительно», 35–44 «хорошо», 45–54 «отлично». Модули 1 и 2 **независимы**.

## 2. Что добавлено в этой лабораторной как архитектурное предложение

| Решение | Статус | Причина |
| --- | --- | --- |
| Два логических контура: DMZ и приватная подсеть | Проектное | Доступ к Analytics и БД только внутри сети |
| Внешний HTTPS через Nginx/TLS, 443 | Проектное | Безопасный вход пользователей |
| Внутренний Backend HTTP, TCP 8000 | Проектное | Пример проксирования от Nginx |
| Analytics gRPC, TCP 50051, mTLS | Проектное | Вызов Backend → Analytics |
| Notifications gRPC, TCP 50052, mTLS | Проектное | Совместимость вызовов Backend/Analytics |
| PostgreSQL/TLS, TCP 5432 | Проектное | Типовой интерфейс к хранилищу |
| Реплика PostgreSQL, WAL/TCP 5432 | Возможное расширение | Демонстрация резервирования; не развернута |
| Финансовая ИС `finance_scholarship` | **Требует согласования** | В методичке требуется внешняя финансовая система, но предметная область напрямую её не предполагает |

Порты и узлы не следует выдавать за уже существующую инфраструктуру МГТУ «СТАНКИН».

## 3. Вопрос о финансовой системе

Методичка (раздел 1.4) требует **две корпоративные системы и одну внешнюю финансовую систему**. Пример методички рассчитан на «Умную парковку» с банковским эквайрингом. Для ИС аттестации логичнее рассматривать **планируемую передачу утверждённых результатов в финансовый модуль стипендиального обеспечения**. При этом:

- В изначальной L1/L2 такой интеграции не было;
- На L0 она подписана «ПЛАН» и отделена от фактически проектируемого набора;
- Согласуйте с преподавателем допустимость такой интерпретации или замену требования образовательной интеграцией.

Нельзя утверждать, что финансовая ИС существует, имеет открытый API или уже получает данные.

## 4. Граница ответственности

ЛР4 моделирует взаимодействия и размещение, **не реализует новые сетевые сервисы**. Прототип ЛР3 `rating_calc` остаётся вычислительным классом. Репозиторий, gRPC-сервер, контейнеризация и репликация описаны на архитектурном уровне.

## 5. Особенность C4

L0 показывает предприятие/несколько систем; L1 — один центральный продукт, акторы и внешние системы; Dynamic — упорядоченные вызовы в конкретном сценарии; Deployment — узлы исполнения уже существующих контейнеров. Не нужно рисовать все классы Strategy в Deployment: это внутренняя деталь `rating_calc`, а не отдельный контейнер.
