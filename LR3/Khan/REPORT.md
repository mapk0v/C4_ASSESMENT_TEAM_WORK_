## 1. Цель работы

Детализировать компонент `rating_calc` сервиса аналитики (C4 L3) до уровня программных классов (L4), реализовать типизированный объектно-ориентированный Python-прототип, применить паттерн Strategy и принципы SOLID.

## 2. Исходные сведения и требования

По методическому пособию ЛР №3 требует UML Class Diagram для выбранного компонента, работающий прототип на Python (или стеке проекта), обязательный Strategy, строгие аннотации типов и SOLID (раздел 1.3, стр. 6). В L3 компонент `rating_calc` находится внутри `analytics_service`, вызывается `analytics_coordinator` и логически взаимодействует с `analytics_repo`.

В группе ИДБ-23-12 по представленному расписанию шесть дисциплин:

1. Информационная безопасность.
2. Стратегии развития ИТ бизнеса.
3. Применение методов машинного обучения в информационно обоснованных решениях.
4. Компьютерная графика и геометрическое моделирование.
5. Корпоративные информационные системы.
6. Информационные системы и технологии.

Со слов студента, учебный период сентября–декабря включает два независимых модуля с одинаковым набором дисциплин; по каждой дисциплине в конце каждого модуля выставляется самостоятельный балл от 0 до 54: 45–54 — отлично; 35–44 — хорошо; 25–34 — удовлетворительно; ниже 25 — не сдал. **Баллы модулей не влияют друг на друга.** Расписание подтверждает перечень дисциплин, но не формулы агрегированного рейтинга.

## 3. Постановка задачи

1. Хранить оценки как комбинацию `(student_id, discipline_code, academic_year, module)` и `mark`.
2. Для конкретного студента и модуля классифицировать баллы по порогам 0–54 и подсчитывать несданные результаты.
3. Вычислять аналитический показатель по нескольким дисциплинам **без смешивания модулей**.
4. Предусмотреть подмену алгоритма вычисления без изменения `RatingCalculator`.
5. Проверить ограничения входных данных, независимость модулей и корректность всех границ оценивания.

**Проектное допущение:** поскольку официальный способ вычисления интегрального рейтинга по дисциплинам не дан, реализуются три иллюстративные стратегии: среднее, медиана и минимальный балл. Это не официальные итоговые оценки МГТУ «СТАНКИН».

## 4. Проектирование UML Class Diagram

Исходник диаграммы — `class_diagram.puml`. Она содержит интерфейс `RatingStrategy`, конкретные реализации `AverageStrategy`, `MedianStrategy`, `MinimumStrategy`, контекст `RatingCalculator`, классы данных `Student`, `Discipline`, `ModuleGrade`, `RatingSummary`, перечисления `ModuleNumber` и `GradeCategory`.

Связи: `RatingCalculator` использует интерфейс стратегии, три конкретных класса реализуют его, а данные поступают через `ModuleGrade`. В отличие от диаграммы компонентов L3, диаграмма классов L4 не изображает PostgreSQL/gRPC как внутренние классы `rating_calc`.

## 5. Описание реализации

**`models.py`:** типизированные неизменяемые (`frozen=True`) dataclass-модели, перечисления модулей и категорий, валидация 0–54, признак `not_passed` (балл ниже 25).

**`strategies.py`:** абстрактный класс `RatingStrategy` и реализации `calculate(grades) -> Decimal`:

- `AverageStrategy`: сумма оценок / число оценок;
- `MedianStrategy`: медиана оценок;
- `MinimumStrategy`: наименьшая оценка.

**`calculator.py`:** `RatingCalculator` хранит стратегию в `_strategy`; метод `set_strategy` меняет её во время выполнения. Метод `calculate_rating` выбирает записи по студенту, году и **одному** модулю, проверяет отсутствие дублей, вычисляет результат и число несданных дисциплин.

**`catalog.py`:** шесть дисциплин расписания с внутренними кодами.

Отсутствующая оценка не приравнивается к нулю; если в модуле нет ни одной оценки, возвращается ошибка. В прототипе предусмотрена ровно одна текущая оценка по конкретной дисциплине и модулю; для истории пересдач потребуется дополнительная модель событий.

## 6. Паттерн Strategy

`RatingStrategy` задаёт единый контракт `calculate`. Три конкретные стратегии реализуют разные способы вычисления. `RatingCalculator` зависит от интерфейса, а не от конкретного алгоритма; переключение стратегии выполняется через `set_strategy`. Благодаря этому новую стратегию можно добавить без изменения существующего контекста.

## 7. Принципы SOLID

- **S:** модели хранят данные и обеспечивают ограничения; стратегии только вычисляют; калькулятор координирует расчёт.
- **O:** новую стратегию добавляют новым классом без изменения `RatingCalculator`.
- **L:** любая стратегия реализует единый контракт и может быть подставлена вместо другой при соблюдении возвращаемого диапазона.
- **I:** интерфейс содержит только один необходимый метод `calculate`.
- **D:** `RatingCalculator` зависит от `RatingStrategy`, а не от конкретных `AverageStrategy` и др.

Локальный запуск завершился успешно: `Ran 15 tests ... OK`.

## 10. Вывод

Разработаны UML Class Diagram L4 и работающий объектно-ориентированный Python-прототип компонента `rating_calc`. Реализованы три взаимозаменяемые стратегии, строгие аннотации типов и проверки данных. Главная предметная особенность — **два полностью независимых модуля**; шкала баллов применена к каждой дисциплине отдельно. Прототип логически согласуется с `analytics_service` / `analytics_coordinator` / `rating_calc` предыдущего уровня C4.
